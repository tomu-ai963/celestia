## 1. 全体の構成

```
1フレーム
 ├─ ① HDR 層（レイヤー1）: 天の川メッシュ → 星（加算）
 │     描画先: RGBA16F のレンダーターゲット 1 枚（深度なし）
 ├─ ② ブルーム（UnrealBloomPass。①の RT に加算で書き戻す）
 ├─ ③ 最終パス: トーンカーブ → sRGB 変換 → ディザ → 画面
 └─ ④ オーバーレイ層（レイヤー0・既定）: 星座線・黄道・地平線・ラベル・天体スプライト・軌跡・占星術レイヤー
       描画先: 画面へ直接（autoClear を切り、深度だけ消してから）
```

2層に分ける理由は 3 つある。

- **線の見た目を変えない**。今の線とラベルは sRGB の値のままアルファ合成されている（色管理なし）。全部を線形の HDR に入れると、不透明度 0.15 の線は符号値で約 2.5 倍明るくなり、不透明度を全部調整し直すことになる。別経路なら今と同じ式で合成される
- **線のアンチエイリアスを保てる**。キャンバスの MSAA（388行目 `antialias:true`）は画面へ直接描くときだけ効く。レンダーターゲットに線を描くなら `samples` 付きの浮動小数 RT が要り、スマホで重い
- **検証が単純になる**。オーバーレイだけを出した画面は、移行の前後で画素単位の比較ができる（G.3）

レイヤーの割り当ては「HDR に入れる 3 個（天の川・星2組）だけをレイヤー1へ移し、残りは既定のレイヤー0のまま」とする。`Object3D.layers` は子に引き継がれないので、後から足した物が既定でオーバーレイ側に入るほうが安全で、`Raycaster`（1434〜1439行目）も既定のレイヤー0のまま動く。

**副作用が1つある。** 今は線が深度を書き、星がそれを深度テストするので、線の真後ろの星の画素は描かれていない（線は `depthWrite` 既定 true、星は 464行目で `depthWrite:false` だが `depthTest` は既定 true）。2層にすると星が先に全部描かれ、その上に線が合成される。線の下の画素の明るさがわずかに変わるが、位置は変わらない。

| S4 | 旧来固定の 2 行を外して色管理をオンにし、A.2 の 3a〜3c を直す | オーバーレイは許容差つきで一致（下記）。星と天の川は画素単位で一致 | 位置データが一致 |

S3 で旧来の設定に固定するのは、r187 の `ColorManagement.js` 46行目で `enabled === false` のとき色変換が何もしないことを確認したため。この段階の期待値は「差が 0 画素」で、差が出たら移行の不具合として扱える。

S4 では完全一致にならない。スプライトのテクスチャを sRGB として読むと、拡大・縮小の補間が線形の値で行われるようになり、グローの勾配とラベルの縁が数階調ずれる。許容差は「1 チャンネルあたり 4/255 以下、差のある画素は全体の 1% 以下」を初期値とし、実測値を報告する。位置は G.3 の位置データで別に確かめる。

色管理をオンにする段階（S4）を省いて旧来の設定のまま進む道もある。ただし HDR 層の天の川メッシュと、将来の WebGPU 移行は色管理オンが前提になるので、ここで済ませる。

## B. 明るさの描き方

### B.1 今の方法の評価

今は等級を「点の大きさ」と「明るさ」に経験式で分けている（428〜429行目）。実データに当てた結果:

| 等級 | `magSize` | `magBright` | カメラからの距離 1600 での点の大きさ |
|---:|---:|---:|---:|
| −1.44（シリウス） | 20.00 | 1.05 | 7.50 px |
| 0 | 12.50 | 1.05 | 4.69 px |
| 2 | 6.47 | 0.77 | 2.43 px |
| 4 | 3.35 | 0.62 | 1.70 px |
| 6.5 | 2.10 | 0.54 | 1.70 px |

- 8,920 個のうち **8,729 個（98%）が最小の 1.7 px**（460行目の `max(…, 1.7)`）に張り付いている
- 明るさの比は最大でも **1.94 倍**（1.05 ÷ 0.54）。Pogson の式では同じ範囲が **1,500 倍**ある
- つまり画面上のほとんどの星は「同じ大きさ・ほぼ同じ明るさの点」で、これがざらつきの正体。このまま星を 4 万個に増やすと、均一な砂のようになる
- 点の大きさがカメラからの距離で変わる（460行目の `600./-mv.z`）。星は無限遠にあるので、物理的には距離で変わる理由がない
- 点の大きさは実画素で指定されていて、pixelRatio（389行目）を掛けていない。高精細な画面ほど星が小さく見える

### B.2 等級から明るさ・大きさへ

出発点は Pogson の式。

```
F(m) = 10^( −0.4 · γ · (m − m_white) )
```

- `m_white`: 最小サイズの星のピークが 1.0（表示上の白）になる等級。**露出に当たる値**で、肉眼モード 3.0、双眼鏡モード 4.5 を初期値にする
- `γ`: 1.0 が Pogson の式そのまま。見た目の調整用のつまみとして残すが、初期値は 1.0

星は実画素より小さいので、像をガウス関数で描く。暗い星は最小の幅のまま明るさだけを変え、明るい星はピークを頭打ちにして幅を広げる。

```
s      = HDR 層の pixelRatio（実画素 / CSS画素）
σ0     = max(0.8, 0.7·s)                  … 最小の幅（実画素）
F ≤ P_max のとき:  peak = F,      σ = σ0
F > P_max のとき:  peak = P_max,  σ = σ0 · sqrt(F / P_max)
像:     I(r) = peak · exp(−r² / 2σ²)      … r は星の中心からの距離（実画素）
点の大きさ: gl_PointSize = min(6σ + 1, 端末の上限)
```

`P_max` の初期値は 4.0。どちらの場合も総光量は `2π·σ0²·F` で、**等級と総光量の関係は Pogson の式のまま保たれる**。明るい星が大きく見えるのは、目やフィルムで起きることと同じ（飽和した芯のまわりに光が広がる）。

初期値での値（`m_white = 3.0`、`P_max = 4`、`σ0 = 0.8`。右端は B.4 のトーンカーブを通した 8 ビットの値）:

| 等級 | F | ピーク | σ（px） | 画面の値 |
|---:|---:|---:|---:|---:|
| −1.44 | 59.70 | 4.00 | 3.09 | 255 ＋ ブルーム |
| 0 | 15.85 | 4.00 | 1.59 | 255 ＋ ブルーム |
| 1 | 6.31 | 4.00 | 1.00 | 255 ＋ ブルーム |
| 2 | 2.51 | 2.51 | 0.80 | 255 |
| 3 | 1.00 | 1.00 | 0.80 | 244 |
| 4 | 0.398 | 0.398 | 0.80 | 169 |
| 5 | 0.158 | 0.158 | 0.80 | 111 |
| 6 | 0.063 | 0.063 | 0.80 | 71 |
| 6.5 | 0.040 | 0.040 | 0.80 | 56 |

双眼鏡モード（`m_white = 4.5`）では 8.0 等が 56、6.5 等が 111、シリウスは σ = 6.17 px になる。白に達する星は肉眼モードで 179 個（3.0 等以下）、双眼鏡モードで 925 個（4.5 等以下）。

決めた理由:

- **σ0 = 0.8**: ガウス像を画素の中心で標本化したとき、総光量の揺れは σ = 0.5 で 5.9%、0.6 で 0.66%、0.7 で 0.05%、0.8 で 0.00%（計算値）。0.7 以上なら星が画素の境目をまたいでも総光量は変わらない。ただし「いちばん明るい 1 画素」の値は σ = 0.8 で 48%、σ = 1.0 で 28% 揺れる。カメラは常にゆっくり回っている（1472行目）ので、揺らぎが目につく場合は 1.0 まで上げる
- **CSS 画素を基準にする**: σ0 を pixelRatio に比例させると、総光量が CSS 画素あたりで一定になり、端末の解像度で星の明るさが変わらない
- **P_max = 4**: ピークを無制限にすると、1 画素だけ極端に明るい値がブルームの縮小で不安定になり、ちらつく。頭打ちにして面積で受ければ光量は同じで安定する
- **距離で大きさを変えない**: 今の `600./-mv.z` はやめる。位置には関係しない

表示限界のフェード:

```
fade = 1 − smoothstep(m_limit − 0.5, m_limit, m)        … F に掛ける
```

`m_limit` は肉眼モード 7.0、双眼鏡モード 8.5。どちらもデータの上限より 0.5 等深いので、定常状態では何も欠けない。切り替えのときにこの値を動かして、星が明るい順に現れるようにする（C.3）。

シェーダに渡すのは等級そのもの（`aMag`）と線形の色（`aColor`）で、`F`・`peak`・`σ` は頂点シェーダで計算する。露出や表示限界を変えてもバッファを作り直さずに済む。同じ式を JS の純関数（`src/starlight.mjs`）にも持ち、`npm test` で値を固定する。

### B.3 B−V 色指数から色へ

今の方法（412〜425行目）は 2 段になっている。

1. B−V → 有効温度: Ballesteros (2012) の式 `T = 4600 (1/(0.92·BV + 1.7) + 1/(0.92·BV + 0.62))`
2. 温度 → RGB: 黒体の色の近似式（係数は Tanner Helland の当てはめと一致する）。最後に白へ 15% 寄せる

評価:

| 点 | 内容 |
|---|---|
| 良い | 1 段目は簡潔で、表示用には十分。太陽（B−V 0.65）で 5,778 K になる |
| 問題1 | 2 段目の出力は sRGB の値で、最大のチャンネルが 1 になるよう正規化されている。**同じ等級でも色によって輝度が変わる**。線形に直して輝度を計算すると、B−V −0.3 の青い星は 0.64、B−V 2.0 の赤い星は 0.62、太陽型は 0.92（計算値）。V 等級は輝度そのものなので、色で 3〜4 割暗くなるのは誤り |
| 問題2 | sRGB の値をそのままフラックスに掛けると、線形の HDR では色が薄く転ぶ |
| 問題3 | 2 段目は 6,600 K で式が切り替わる当てはめで、導関数が不連続 |
| 問題4 | 色指数が欠けている星（6.5 等以下で 40 個、8.0 等以下で 112 個）は 0.63 で代用（`build-stars.mjs` 21行目）。これはそのままでよい |

改善案:

1. B−V → T は今のまま（Ballesteros 2012）。T は 1,667〜25,000 K に収める
2. T → 色度 (x, y): 黒体軌跡の 3 次スプライン近似（Kang et al. 2002）
   ```
   x = −0.2661239e9/T³ − 0.2343589e6/T² + 0.8776956e3/T + 0.179910      (1667 ≤ T ≤ 4000)
   x = −3.0258469e9/T³ + 2.1070379e6/T² + 0.2226347e3/T + 0.240390      (4000 < T ≤ 25000)
   y = −1.1063814x³ − 1.34811020x² + 2.18555832x − 0.20219683           (1667 ≤ T ≤ 2222)
   y = −0.9549476x³ − 1.37418593x² + 2.09137015x − 0.16748867           (2222 < T ≤ 4000)
   y =  3.0817580x³ − 5.87338670x² + 3.75112997x − 0.37001483           (4000 < T ≤ 25000)
   ```
   Planck の式を等色関数の解析近似（Wyman ほか 2013）で積分した値と比べ、6,500 K で (0.3135, 0.3237) と一致、最大の差は 1,667 K で 0.003 だった（計算値）
3. (x, y) と Y = 1 から XYZ、さらに線形 sRGB（Rec.709、D65）へ。負のチャンネルが出たら（低温の赤）、白を混ぜて色域に収める
4. 彩度の調整: 線形のまま `c = 1 + (c − 1)·s`。初期値は s = 0.85（今の「白へ 15%」に相当）
5. **輝度で正規化**: `c /= (0.2126 r + 0.7152 g + 0.0722 b)`。色がどうであれ輝度は 1 になり、明るさは等級だけで決まる

結果の例（s = 1 のとき。チャンネルが 1 を超えるのは HDR なので問題ない）:

| B−V | T | 今の値（sRGB） | 改善案（線形・輝度 1） |
|---:|---:|---|---|
| −0.3 | 16,602 K | 0.74, 0.83, 1.00 | 0.77, 0.99, 1.76 |
| 0.0 | 10,125 K | 0.82, 0.88, 1.00 | 0.87, 0.99, 1.44 |
| 0.65 | 5,778 K | 1.00, 0.96, 0.92 | 1.11, 0.98, 0.91 |
| 1.5 | 3,794 K | 1.00, 0.82, 0.67 | 1.47, 0.91, 0.48 |
| 2.0 | 3,169 K | 1.00, 0.76, 0.55 | 1.69, 0.86, 0.32 |

実装は JS の純関数にして `src/starlight.mjs` に置き、頂点の色属性として渡す。シェーダ側には色の計算を持たせない。芯が白く飽和し、にじみに色が残るのは、チャンネルごとにトーンカーブをかける（B.4）ことで自然に出る。

### B.4 HDR・トーンマッピング・ブルーム

#### B.4.1 描画の流れ

r187 には選択肢が 3 つある。

| 方法 | 内容 | 評価 |
|---|---|---|
| ① 自前の RT 1 枚 ＋ `UnrealBloomPass` ＋ 自前の最終パス | `setRenderTarget` で HDR 層を描き、`bloomPass.render(renderer, null, rt)` でブルームを書き戻し、全画面の 1 枚で画面へ | **推奨**。浮動小数 RT が全解像度で 1 枚で済む。大きさを描画バッファの整数値に直接合わせられる。最終パスにディザを入れられる |
| ② `EffectComposer` ＋ `RenderPass` ＋ `UnrealBloomPass` ＋ 最終パス | 移行ガイド（r154→155）が案内する定番 | 結果は同じ。全解像度の RT が 2 枚になる（スマホで約 10 MB 多い）。大きさが `幅 × pixelRatio` の小数になりうる（`EffectComposer.js` 69行目） |
| ③ `WebGLRenderer({ outputBufferType: HalfFloatType })` ＋ `renderer.setEffects([...])` | r187 の本体に入っている新しい仕組み（`WebGLOutput.js`） | 将来の `WebGPURenderer` と同じ引数名で魅力はある。ただしトーンマッピングは組み込みか `CustomToneMapping`（シェーダ文字列の差し替え）に限られ、変換後のディザを足せない。画面への描画がすべてこの経路を通るので、オーバーレイを別経路にするには毎フレーム設定を切り替える必要がある |

①の骨組み（確認済みの API だけを使っている）:

```js
// 起動時
const size = renderer.getDrawingBufferSize(new THREE.Vector2());   // 整数。canvas.width/height と同じ
const rt = new THREE.WebGLRenderTarget(size.x, size.y,
  { type: THREE.HalfFloatType, depthBuffer: false });
const bloom = new UnrealBloomPass(size, 0.2, 0.4, 1.0);             // 解像度, 強さ, 半径, 閾値
bloom.highPassUniforms.smoothWidth.value = 0.5;
const finalQuad = new FullScreenQuad(finalMaterial);                // three/addons/postprocessing/Pass.js

// 毎フレーム（1479行目の renderer.render を置き換える）
camera.layers.set(1);                       // HDR 層
renderer.setRenderTarget(rt); renderer.clear(); renderer.render(scene, camera);
if (bloomOn) bloom.render(renderer, null, rt);   // needsSwap=false。rt に加算で書き戻す
renderer.setRenderTarget(null);
finalQuad.render(renderer);                 // トーンカーブ → sRGB → ディザ。アルファは 1
renderer.autoClear = false; renderer.clearDepth();
camera.layers.set(0);                       // オーバーレイ
renderer.render(scene, camera);
renderer.autoClear = true;
```

- **RT の大きさは `getDrawingBufferSize` の整数値を使う**。CSS の幅に pixelRatio を掛けた小数を使うと、RT と画面で半画素ずれる余地ができる
- HDR 層の物は互いを隠さないので、深度バッファは持たない（星は `depthTest:false`・`depthWrite:false`、天の川も同じ）
- リサイズ（1442〜1446行目）では `rt.setSize` と `bloom.setSize` も呼ぶ
- 半精度の RT へ描けるかは `EXT_color_buffer_half_float` か `EXT_color_buffer_float` の有無で決まる（r187 `WebGLCapabilities.js` 42行目と同じ判定）。無い端末は E.3 の Q0 へ落とす

#### B.4.2 最終パス

```glsl
uniform sampler2D tHdr; uniform float uKnee; varying vec2 vUv;
vec3 toneCurve(vec3 x) {                       // uKnee まで恒等、そこから指数で 1 へ
  vec3 hi = uKnee + (1.0 - uKnee) * (1.0 - exp(-(x - uKnee) / (1.0 - uKnee)));
  return mix(x, hi, step(vec3(uKnee), x));
}
void main() {
  gl_FragColor = vec4(toneCurve(texture2D(tHdr, vUv).rgb), 1.0);
  #include <colorspace_fragment>               // 画面へ描くとき sRGB へ（r154 以降の名前）
  gl_FragColor.rgb += (hash(gl_FragCoord.xy) + hash(gl_FragCoord.xy + 17.0) - 1.0) / 255.0;  // 三角分布のディザ
}
```

`hash` は画素の座標から 0〜1 の乱数を返す関数で、実装側で用意する（骨組みなので省いている）。全画面の描画には `three/addons/postprocessing/Pass.js` の `FullScreenQuad` を使う。

#### B.4.3 トーンマッピングの方式

**自前のカーブ（0.75 まで恒等、そこから `k + (1−k)(1 − e^{−(x−k)/(1−k)})`）**を使う。傾きは 0.75 で 1 のままつながる。

組み込みを使わない理由は、どれも暗部を動かすから。灰色を入力したときの 8 ビットの出力（r187 の `tonemapping_pars_fragment.glsl.js` の式を写して計算した。露出 1）:

| 線形の入力 | 相当する星（肉眼モード） | Reinhard | ACES | AgX | Neutral | **自前** | 変換なし |
|---:|---|---:|---:|---:|---:|---:|---:|
| 0.0063 | 8.5 等 | 18 | 4 | 9 | 1 | **19** | 19 |
| 0.0158 | 7.5 等 | 33 | 16 | 30 | 5 | **34** | 34 |
| 0.040 | 6.5 等 | 55 | 41 | 61 | 25 | **56** | 56 |
| 0.18 | 4.9 等 | 109 | 127 | 128 | 105 | **118** | 118 |
| 0.75 | 3.3 等 | 175 | 216 | 191 | 219 | **225** | 225 |
| 1.0 | 3.0 等 | 188 | 226 | 202 | 240 | **244** | 255 |
| 4.0 | 1.5 等より明るい星の芯 | 231 | 250 | 239 | 253 | **255** | 255 |

- **Neutral** は最小チャンネルから `x − 6.25x²` を引くので、暗い灰色がつぶれる（6.5 等が 56 → 25、7.5 等が 34 → 5）。暗い星がほぼ消える
- **ACES** も暗部を下げる（6.5 等が 41、8.5 等が 4）。加えて露出に 1/0.6 が掛かっている
- **AgX** は暗部と中間を持ち上げ、明部を抑える。等級と明るさの比が全域で変わる
- **Reinhard** は暗部はほぼ保つが、白に届かない（4.0 でも 231）
- 自前のカーブは 0.75 までは入力そのまま。**3.3 等より暗い星では、画面の線形の光量が Pogson の式の比のまま出る**。チャンネルごとにかけるので、明るい芯は白へ寄り、色はにじみの側に残る

露出は `renderer.toneMappingExposure` を使わず、`m_white`（B.2）で持つ。星の式の中で露出の意味がはっきりするため。

#### B.4.4 ブルームの初期値

| 値 | 初期値 | 理由 |
|---|---:|---|
| 閾値 `threshold` | 1.0 | 表示上の白を超えた分だけをにじませる。白に届かない星（肉眼モードで 3.0 等より暗い 8,741 個）はにじまないので、数を増やしても空が白くかすまない |
| 閾値の幅 `smoothWidth` | 0.5 | 既定は 0.01 で、ほぼ段差（`UnrealBloomPass.js` で `highPassUniforms.smoothWidth = 0.01`）。星が画素をまたぐとき、閾値の前後でにじみが点滅するのを避ける |
| 強さ `strength` | 0.2 | 合成の式に係数 3 が掛かっている（`bloom = 3.0 * bloomStrength * (…)`）ので、実効は 0.6。下の見積もりから |
| 半径 `radius` | 0.4 | 5 段のぼかしの配分。0 は近く寄り、1 は遠く寄り。近い側をやや重くする |

強さの見積もり。ぼかしは 5 段で、各段の幅は元の解像度で約 4・13・37・96・235 px（カーネル 6, 10, 14, 18, 22 の 1/3 を σ とし、半分ずつの解像度で重ねた値）。星の閾値を超えた光量を W_b とすると、芯の近くのにじみは `3 · strength · W_b · 0.0107` 程度になる。

| 星 | F | W_b | にじみの中心（strength 0.2） |
|---|---:|---:|---:|
| シリウス（−1.44 等） | 59.7 | 約 181 | 約 1.16 |
| 1.0 等 | 6.3 | 約 19 | 約 0.12 |
| 2.0 等 | 2.5 | 約 6 | 約 0.04 |

シリウスには半径 15〜30 px ほどのはっきりした光芒が付き、1 等星には淡く付き、2 等星ではほぼ見えない。**ブルームは線形の畳み込みなので、にじみが見える半径はフラックスに応じて自然に決まる**。等級ごとの大きさを手で指定する必要がない。

これらは計算上の見積もりで、実機では調整が要る（H-2）。調整の順番は「`m_white` → `P_max` → `strength` → `radius`」。

### B.5 星を増やしてもざらつかないようにする方法

| 原因 | 対策 | 効く理由 |
|---|---|---|
| 暗い星が全部同じ明るさ・同じ大きさ（B.1） | Pogson のフラックスをそのまま使い、下限を設けない | 0.5 等暗くなるごとに数は約 1.5〜1.7 倍に増えるが、1 個の光量は 0.63 倍になる。暗い星は「点の粒」ではなく淡い地になる |
| 1 画素より小さい点のちらつき | 最小の幅 σ0 のガウス像（B.2） | σ ≥ 0.7 px なら総光量が画素の位置によらない |
| 表示限界での打ち切り | 限界の手前 0.5 等をなめらかに消す | 限界ぎりぎりの星の密度の段差が出ない |
| 重なった所の白飛び | 浮動小数の RT で加算してからトーンカーブ | 8 ビットで加算すると密な所から先に飽和する |
| 暗いグラデーションの縞 | 最終パスのディザ（±1/255） | 天の川の淡い勾配が 8 ビットで階段にならない |
| 閾値付近のにじみの点滅 | `smoothWidth` を広げ、`P_max` で芯を頭打ちにする | B.4.4 |
| 距離による大きさの変化 | やめる（B.2） | 手前の星だけ大きくなる不自然さがなくなる |

### C.2 形式は JSON のままにする

HYG の実データで測った（生 / gzip -9 / brotli 11）。

| 段 | 個数 | JSON（今の並び） | バイナリA（黄経・黄緯 Int32、等級・色 Int16、列ごと。12 B/個） | バイナリC（黄経 Uint16、ほか Int16。8 B/個） |
|---|---:|---|---|---|
| 肉眼（≤6.5） | 8,920 | 177.6 / 76.9 / 65.8 KB | 104.5 / 63.2 / 52.2 KB | 69.7 / 47.8 / 44.7 KB |
| 双眼鏡（6.5〜8.0） | 32,567 | **646.5 / 272.8 / 235.3 KB** | 381.7 / 224.0 / 184.2 KB | 254.4 / 166.9 / 159.8 KB |
| （参考）6.5〜8.5 | 52,896 | 1,049.9 / 441.2 / 380.3 KB | 619.9 / 362.3 / 298.9 KB | 413.3 / 269.9 / 258.4 KB |
| （参考）6.5〜9.0 | 74,559 | 1,480.9 / 620.4 / 534.3 KB | 873.8 / 509.6 / 420.4 KB | 582.5 / 379.9 / 366.2 KB |

JSON のままにする理由:

1. **圧縮後の差が小さい**。今と同じ精度を保つバイナリA は、gzip で 272.8 → 224.0 KB（18% 減）。生のサイズでは 41% 減るが、転送されるのは圧縮後
2. **配信側が JSON は圧縮し、バイナリは圧縮しない**。Cloudflare が既定で圧縮する種類の一覧に `application/json` はあるが `application/octet-stream` はない（Cloudflare の圧縮の公式文書）。バイナリは自分で圧縮して `DecompressionStream` で展開する仕組みが別に要る
3. **読み込みとテストが 1 系統で済む**。`tests/stars.test.mjs` 59〜72行目の検査をそのまま双眼鏡の段にも使える。バイトの並び順やヘッダの検査が増えない
4. 精度を落とすバイナリC は 39% 減るが、位置の刻みが 0.001° から 0.0055° に粗くなる。画面では最大 0.1 px 程度で見えない差だが、肉眼の段と計算経路が分かれる

**バイナリに切り替える目安**: 1 段が gzip で 500 KB を超える、または 10 万個を超えるとき（8.5 等より深くするか、別のカタログへ移るとき）。そのときはバイナリC を自前で gzip し、拡張子 `.bin` で配る。

サイズの上限: `data/stars-deep.json` は 700 KB 以下（今の値 646.5 KB に余裕を足した）。25 MiB の制約には 2 桁の余裕がある。

### C.3 後から読み込む流れ

```
[肉眼] ──切り替え──▶ 読み込み中 ──成功──▶ [双眼鏡]
                        │
                        └─失敗──▶ [肉眼] に戻し、理由を1行出す
```

1. 「天球の表示」の中（315〜323行目）に「双眼鏡の空」のトグルを足す。既定はオフ
2. 初めてオンにしたとき `fetch('data/stars-deep.json')`。2 回目以降は作った点群を出し入れするだけ
3. 読み込み中はトグルの文言を「双眼鏡の空（読み込み中…）」にする。画面中央の `#starload`（265行目）は使わない。空はもう見えていて、隠す理由がない
4. 届いたら 2 つ目の `THREE.Points` を作り、`starGroup`（439行目）に足す。`celestialGroup` の子なので、歳差は肉眼の段と同じ行列で乗る。マテリアルと uniform は肉眼の段と共有する

| 上限 | 個数（合計） | 評価 |

### D.2 推奨

**第1候補は NASA SVS の `milkyway_2020_4k_gal.exr`**。

1. **明るい星が入っていない**。celestia は星を自前で描くので、星入りの画像を使うと同じ星が二重になる（画像の中のにじんだ星と、その上の鋭い点）。Tycho-2 は 11 等前後までなので、8.0 等までを自前で描く今回の設計とぶつからない
2. **座標と投影が文章で明記されている**。ほかの 2 つは向きを画像から推し量ることになる
3. **線形の値で配られている**。暗い部分をどこまで持ち上げるかを、8 ビットへ落とす前に決められる
4. 銀河座標版は帯が画像の中央の水平な帯に集まるので、圧縮が効きやすい

懸念は 2 点ある。ページにライセンスの記載がなく NASA の一般指針に頼ること、そして元データの Gaia DR2 に対する ESA 側の条件がこの派生画像にどう及ぶかが読み取れないこと（H-4）。

第2候補は ESA/Gaia の EDR3 版。ライセンスが明記されている点は強い。`data/` はすでに CC BY-SA の派生物を置く場所として整理されている（`data/ATTRIBUTION.md`）ので、継承の義務も扱いやすい（ただし 3.0 IGO と 4.0 は別のライセンスなので、ファイル単位で分けて書く）。弱点は星が入っていることと、経度の向きが書かれていないこと。

ESO の写真は見た目の質は高いが、明るい星がすべて写っていて二重になるので、今回の用途には合わない。

採用の最終判断は人間が行う。どれを選んでも D.3 以降の仕組みは同じ。

### D.3 座標の対応

画像は銀河座標 (l, b) の正距円筒で、中心が (0°, 0°)、経度は左へ増える。テクスチャ座標は

```
u = 0.5 − l′/360     （l′ は l を −180°〜+180° に直した値）
v = 0.5 + b/180      （上が北。three.js の画像テクスチャは既定で上の行が v = 1）
```

銀河座標から three.js の座標までは、今の 516〜527・540行目と同じ変換を使う。

```
g  = (cos b · cos l,  cos b · sin l,  sin b)                 銀河直交
q  = x_g·g_x + y_g·g_y + z_g·g_z                             赤道直交 (J2000)
       z_g = 赤道(α 192.85948°, δ +27.12825°)                銀河北極
       x_g = 赤道(α 266.40500°, δ −28.93617°) を z_g に直交化  銀経 0°・銀緯 0°
       y_g = z_g × x_g
e  = (q_x,  q_y·cos ε + q_z·sin ε,  −q_y·sin ε + q_z·cos ε)  黄道直交 (J2000)、ε = 23.4392911°
(X, Y, Z) = (e_x, e_z, −e_y)                                 three.js（src/precession.mjs 207〜209行目）
```

まとめると定数の回転行列 1 つになる。3 つの列は銀河座標の基底の行き先で、計算値は次のとおり。

| 銀河座標の向き | three.js の (X, Y, Z) |
|---|---|
| l = 0°, b = 0° | (−0.0549, −0.0965, 0.9938) |
| l = 90°, b = 0° | (0.4941, 0.8623, 0.1110) |
| b = +90°（銀河北極） | (−0.8677, 0.4971, 0.0004) |

カタログ値のままだと x_g と z_g は 90° から 1.8×10⁻⁶° ずれているだけで、521行目の直交化は丸めの補正にすぎないことも確かめた。

### D.4 メッシュで貼る

画素ごとに逆変換（atan と asin）をする方法は取らない。経度 ±180° の継ぎ目でミップマップの選択が乱れて線が出るため。代わりに、**銀河座標の格子で球のメッシュを作り、頂点に (u, v) を直接持たせる**。

- 格子: 経度 180 分割 × 緯度 90 分割（2° 刻み）。経度 +180° と −180° の列は頂点を重ねて持つ（u = 0 と u = 1）
- 頂点の位置: `R · (X, Y, Z)`。R は今の天の川と同じ 1660（529行目）
- 2° 刻みの平面の三角形で球を近似する誤差は約 θ²/8 = 0.009°。4096 px の画像の 0.1 画素、スマホの画面で 0.3 px
- `celestialGroup` の子にする。歳差は星と同じ行列で乗る
- マテリアルは **`MeshBasicMaterial`**（`map`、`side: BackSide`、`depthTest: false`、`depthWrite: false`、`color` を明るさの倍率に使う）。テクスチャは `colorSpace = SRGBColorSpace`。自前のシェーダは要らない
- `SphereGeometry` は使わない。UV の割り付けの向きに頼ると、左右が反転しても気づきにくい。位置と UV を上の式から自分で作れば、向きは式だけで決まる

変換は `index.html` から `src/galactic.mjs` へ移し、`npm test` で検査する（天文の式は `src/` に置いてテストする、という今の決まりに合わせる）。

### D.6 解像度と容量

| 用途 | 画像 | GPU のメモリ（RGBA8 ＋ ミップマップ） | 1 テクセルの大きさ | ファイルの上限 |
|---|---|---:|---|---:|
| スマホ（既定） | **2048×1024** | 11.2 MB | 0.176°。高さ 1688 px の画面で 5.7 px | 300 KB |
| PC・上位の端末 | 4096×2048 | 44.7 MB | 0.088°。高さ 1688 px で 2.9 px、720 px で 1.2 px | 1.2 MB |

- 8192 px は使わない。GPU で 179 MB になる
- 星を除いた天の川は細かい点を含まないので、2048 px で拡大されても破綻しにくい。暗黒帯の細部は 4096 px のほうが残る
- 形式は WebP（品質 85〜90）。暗くなめらかな所はブロックの乱れが見えやすいので、品質を下げすぎない
- ファイルの上限は見積もり。実際に書き出して測る（H-5）
- `renderer.capabilities.maxTextureSize` が 4096 未満の端末は 2048 px を使う
- 元の EXR（34.8 MB）は 25 MiB を超えるので、リポジトリにも配信物にも入れない。`tools/.cache/`（`.gitignore` 済み）に置き、派生の WebP だけをコミットする

書き出し（`tools/build-milkyway.mjs`、生成物はコミットする。アイコンの `scripts/build-icons.mjs` と同じ扱い）:

1. EXR を読む（three.js の `EXRLoader.parse` を Node で使う案。未検証。H-6）
2. 背景の底上げ分を引く（空の暗い所が黒になるように）
3. 明るい側の 99.5 パーセンタイルが 1.0 になるよう倍率を掛ける
4. sRGB に変換して 8 ビットにし、2 つの大きさで WebP に書き出す
5. 加えた変更を `data/ATTRIBUTION.md` に書く

#### 実装での実測（2026-11-14 追記・S8）

**Gaia の暗い星の粒が残っていた。** `milkyway_2020_4k_gal.exr` で除かれているのは明るい星（Hipparcos と Tycho、11 等前後まで）だけで、Gaia DR2 の暗い星は 1 画素前後の細かい粒として全面に入っている（SVS のページの説明も “omits the bright (Hipparcos and Tycho) stars”）。上の「星を除いた天の川は細かい点を含まない」は誤りで、このため WebP の圧縮が効かず、そのままでは容量の上限に収まらなかった。

元の EXR: 4096×2048、OpenEXR（ZIP 圧縮、半精度、RGB）、34,771,211 B、SHA-256 `fad63b36…9a49`。three.js r187 の `EXRLoader.parse` を Node で使って読めた（H-6 は解決）。EXRLoader の出力は下の行が先。

書き出しの容量（実測。上限は 2048 px 300 KB、4096 px 1.2 MB）:

| 明るさの基準 | ぼかし（4096 px での σ） | 形式・品質 | 4096×2048 | 2048×1024 |
|---|---|---|---:|---:|
| 99.5 パーセンタイル（当初の手順） | なし | WebP 88 | 3,452.8 KB | 733.1 KB |
| 同上 | なし | WebP 75 / 60 / 50 | 2,208.6 / 1,834.5 / 1,631.8 KB | 422.5 / 340.5 / 288.2 KB |

品質を下げるだけでは、4096 px は品質 50 でも上限を超える。

**明るさの基準も変えた。** 99.5 パーセンタイルを 1.0 にすると、どれかのチャンネルが 1 を超える画素が 0.91% あり、ほぼすべてが銀河中心のふくらみに集まって、暗黒帯などの模様が平らな白になった。採用した手順（とむの判断）:

1. 線形の浮動小数のまま、ガウスぼかし（4096 px で σ 1.2 画素 ≈ 0.1°。2048 px では 2×2 の平均を重ねて σ 約 0.6 画素相当）
2. 背景の底上げ分を引く（ぼかした後の輝度の 1 パーセンタイル 0.0017）
3. 画素ごとの最も明るいチャンネルの最大値を 1.0 にする。最大値が 99.99 パーセンタイルの 2 倍を超えていたら孤立した外れ値とみなして 99.99 パーセンタイルを使う決まりにした。実測は 1.045 倍で、最大値（1.000）を使った。1 を超える画素は 0
4. sRGB に変換し、三角分布のディザ（±1 段、種つきの乱数。生成し直しても同じバイト列）をかけて 8 ビットに
5. 銀河中心のふくらみ（1° 角の平均の最大）はテクスチャの値で 0.810（l = 2.11°, b = −2.99°）。表示の倍率は 0.03 / 0.810（双眼鏡の空で 0.06 / 0.810）

画像との対応は、テクスチャの上に D.5 の (u, v) で印を打って確かめた。銀河中心（中心を横切る暗黒帯の上、すぐ下に明るいふくらみ）、大マゼラン雲（塊の中心）、小マゼラン雲（α 13.187°, δ −72.829° で u = 0.65890, v = 0.25389。芯の上）、石炭袋（アクルックスのすぐ隣、経度の大きい側の暗い穴）が合っていた。M31 はこの層では判別できなかった。

### D.7 明るさの初期値

物理的な目安を置く。天の川の明るい部分の表面輝度を約 21 等/平方秒角とすると、1 画素（高さ 720 px で 0.0722° 角 = 260 秒角四方）に入る光は 8.9 等の星 1 個ぶんに当たる。B.2 の式でこれを 1 画素の値に直すと線形で約 0.017（8 ビットで 35 前後）になる。**物理に忠実な天の川は、6.5 等の星の芯（56）より暗い**。暗い空で見る実際の印象とも合う。

初期値は、いちばん明るい所（銀河中心のふくらみ）が肉眼モードで線形 0.03、双眼鏡モードで 0.06 になるよう `color` の倍率を決める。物理値の約 2 倍で、見やすさのための上乗せ。表面輝度の値は記憶に基づく概数なので、目で調整する（H-3）。

### E.3 品質の段階と落とし方

| 段階 | 内容 | 使う場面 |
|---|---|---|
| Q2 | HDR の RT ＋ ブルーム ＋ 最終パス | 既定 |
| Q1 | HDR の RT ＋ 最終パス。**ブルームなし**。明るい星には式で光芒を足す | ブルームが重い端末 |
| Q0 | RT を使わず画面へ直接描く。星のシェーダの中でトーンカーブと sRGB 変換を行う | 浮動小数の RT に描けない端末、Q1 でも足りない端末 |

Q1 と Q0 の光芒: `F > P_max` の星にだけ、幅の広いガウス像を足す。

```
I(r) += uHalo · (2π·σ0²·F) / (2π·σh²) · exp(−r² / 2σh²)       σh = 5·σ0,  uHalo = 0.25（Q2 では 0）
```

Q0 では加算が 8 ビットの sRGB の値のまま行われるので、星が重なった所は Q2 より明るく出る。孤立した星は Q2 と同じ値になる。

落とす順番（軽い順に効く手から）:

1. HDR の解像度を 1.0 → 0.75 にする（pixelRatio が 1 より大きい端末だけ）
2. ブルームを切る（Q2 → Q1）
3. RT をやめる（Q1 → Q0）
4. 双眼鏡の段を `setDrawRange` で 7.5 等まで（16,871 個）に減らす
5. 天の川を 2048 px に固定する

判定:

- 起動時: 浮動小数の RT に描けなければ Q0。`maxTextureSize` で天の川の大きさを決める
- 実行中: 星の読み込みが終わってから 90 フレームのフレーム間隔の中央値を測る。20 ms を超えたら 1 段落とす。落とす方向にだけ動かし、上げ直さない（行き来して見た目が揺れるのを避ける）
- 手動: URL の `q=0|1|2` で固定できる。設定は保存しない（localStorage を使わない今の構成を保つ）

HDR の解像度を下げても、星の位置は変わらない（RT の中の位置が同じ比率で縮むだけ）。オーバーレイは常に全解像度で描くので、線は鈍らない。

## F. 将来の WebGPU 移行

r187 のソースで確認した前提:

- `WebGPURenderer` は `ShaderMaterial` を使えない。自前のシェーダは TSL のノードで書き直す
- **WebGPU の点は 1 px 固定**。大きさを持つ点は、`Sprite` とインスタンスで描く（`PointsNodeMaterial.js` の説明。`PointsNodeMaterial` は `SpriteNodeMaterial` の派生で、`sizeNode` を持つ）
- ブルームは `three/addons/tsl/display/BloomNode.js` にあり、引数は `strength`・`radius`・`threshold`、内部は 5 段・カーネル 6〜22・`smoothWidth` と、`UnrealBloomPass` と同じ作り
- 後処理の入れ物は `RenderPipeline`（r183 で `PostProcessing` から改名）。読み込み口は `three/webgpu` と `three/tsl`

書き方の方針:

| # | 方針 | 理由 |
|---|---|---|
| 1 | 自前の `ShaderMaterial` は**星と最終パスの 2 つだけ**にする。天の川は `MeshBasicMaterial`、オーバーレイは組み込みマテリアルのまま | 組み込みマテリアルは `WebGPURenderer` がそのまま受け取る。書き直すのは 2 つで済む |
| 2 | 計算は JS の純関数に寄せる（`src/starlight.mjs`: 等級→フラックス、フラックス→ピークと幅、B−V→線形 RGB）。シェーダには「属性と uniform から値を組み立てる」部分だけを置く | TSL へ移すときに写す式が減る。`npm test` で値を固定できる |
| 3 | シェーダの式は、入力と出力がはっきりした小さな関数に分ける（`starFlux(mag)`、`starShape(flux)`、`starProfile(r, peak, sigma)`、`toneCurve(x)`） | 1 関数が TSL の `Fn` 1 つに対応する |
| 4 | `gl_PointSize` と `gl_PointCoord` に触れるのは、それぞれ 1 か所にまとめる。式は「幅（実画素）」と「中心からの距離（実画素）」で書く | WebGPU では点をインスタンスの四角形に置き換える。置き換える場所が 2 行で済む |
| 5 | `#ifdef` で枝分かれさせない。Q0・Q1・Q2 の違いは uniform（`uHalo`、`uInlineTone`）で切り替える | TSL にプリプロセッサはない |
| 6 | three.js のシェーダの部品（`#include`）は `colorspace_fragment` だけにする | 部品は WebGL 専用で、TSL には別の仕組み（`renderOutput` など）がある |
| 7 | 色はすべて線形（Rec.709）で扱い、sRGB への変換は最終パスの 1 か所だけにする。色管理はオン（S4） | `WebGPURenderer` は色管理オンが前提 |
| 8 | `gl_FragCoord` の上下や、深度の値の範囲（WebGL は −1〜1、WebGPU は 0〜1）に頼る式を書かない。ディザは向きに関係ない乱数にする | 2 つの API で原点と範囲が違う |
| 9 | 描画の流れを「場面を RT へ → ブルーム → トーンカーブと出力」の 3 段に保つ | `pass()` → `bloom()` → 出力の関数、にそのまま対応する |
| 10 | uniform の名前と単位をそろえる（`uMagWhite`・`uMagLimit`・`uPeakMax`・`uSigmaMin`［実画素］・`uPixelRatio`） | 対応表を作らずに移せる |

2 層の構成（HDR 層のあとにオーバーレイを直接重ねる）が `RenderPipeline` で同じように組めるかは確かめていない（H-9）。

- `window.__celestia.ready`: 星のデータを読み終え、2 フレーム描いたら解決する Promise
- `window.__celestia.probe()`: 画面上の位置を返す。対象は肉眼の星 8,920 個すべて、星座線の全頂点、12 天体、黄道と地平線の頂点。**実際に描画に使っているジオメトリの頂点**に、`matrixWorld` とカメラの行列を掛けて CSS 画素へ直す。小数 4 桁で丸める

撮影スクリプト（`tools/shoot.mjs`）は Playwright を開発用依存に足して作る案。`npm test` には入れず、`npm run verify:visual` のように別の命令にする。Google Fonts（`index.html` 26〜28行目）への通信は遮断する。ラベルのキャンバス（570行目）はフォントが届く前に描かれることがあり、撮るたびに字形が変わりうるため。

### G.3 位置が動いていないことの確かめ方

見た目を変える段階では画像どうしを直接比べられないので、3 つの方法を組み合わせる。

| 方法 | 何を確かめるか | 合格の条件 | 使う段階 |
|---|---|---|---|
| ① 位置データの比較 | `probe()` の出力を、S0 で撮った基準と比べる | 全点で差が 0.001 px 以下 | 全段階 |
| ② 画像の完全一致 | 同じ条件のスクリーンショットを画素ごとに比べる | 差のある画素が 0（実測値を報告する） | S1〜S3 は全画面。S5 以降は `layers=overlay` の画面を S4 と比べる |
| ③ 星の重心 | `layers=sky&bloom=0` の画面で、明るい順に 200 個の星について、まわり ±4 px の重心と ① の位置を比べる | 差が 0.5 px 以下 | S5 以降 |

- ① は計算上の位置が同じであることを、② と ③ はそれが実際の画素に出ていることを示す。「星・星座線・惑星の位置が一致する」の判定は、S1〜S4 は ①＋②、S5 以降は ①＋②（オーバーレイ）＋③（星）で行う
- **比べる 2 枚は必ず同じ機械・同じブラウザ・同じウィンドウの大きさで撮る**。GPU やドライバが違うと、線の塗り方が 1 画素単位で変わる
- ブルームのにじみは位置の検査に使わない。縮小した格子の上でぼかすので、にじみの重心は芯から 1 px ほどずれうる。芯は直接描いているのでずれない
- 基準の位置データ（JSON）は機械に依存しないので `tests/visual/` にコミットする。画像は機械に依存するので、出力先を `.gitignore` に入れてコミットしない
